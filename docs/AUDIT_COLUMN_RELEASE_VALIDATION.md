# TC-311 release validation

Failure inventory, recorded before release integration changes:

- Ordinary browser CI silently skips the opt-in column-audit specs. The release
  gate must invoke the test-only real router/store/worker harness, with a
  representative completion/reopen/stale/retry journey and retained artifacts.
- Running those specs against the production executable would omit fixture
  controls. Keep the harness separate and reuse the already built frontend.
- Retrieval can select incidental audit prose, mistake tests for implementation,
  miss ordinary-English source owners, or turn missing evidence into reopening.
  Actual GitHub and the configured evidence-only model must be tested separately
  from the scripted integration harness before promotion.
- A read/run agent grant is not human Apply authorization. Current beta uses
  Tailnet human assertions; an isolated disabled-auth synthetic human is only an
  integration check. Neither a forged assertion nor a raw session is acceptable.
- Schema 42 can appear compatible under retained SQL while an actual retained
  release executable fails readiness or loses subsequent writes. Exercise each
  actual retained release on a populated upgraded copy; rollback changes images,
  never restores an older database.
- A snapshot or copied account can accidentally target live storage, expose
  private content, or race credential refresh. Use private independent paths,
  check credential lifetime before inference, keep secrets on the app VM, and
  emit aggregate receipts only. Preserve both historical live audit attempts.
- A goal immediately followed by an acceptance heading can swallow that heading
  as goal continuation, dropping every acceptance condition. A populated capture
  must preserve both labeled sections with or without a blank separator before
  evaluation; multiline condition text and exact source lines must remain intact.

Before promotion, TC-311 requires actual useful model judgments, legitimate
human completion/reopening/stale outcomes, populated compatibility and a fresh
verified online backup. Parent owns review, PR/CI and exact-revision promotion.
The implementation worker must leave this task active and report remaining gates.

Diagnostic failure inventory (recorded before diagnostic implementation): v2
decode, captured identity/condition identity, invented or cross-criterion citation,
missing baseline proof, invalid basis, unavailable destination, lifecycle mismatch,
and publication failures currently collapse into one public error. Discovery
inference, decoding, schema shape, candidate membership, bounded line range and
deadline failures likewise collapse into unavailable. Preserve existing public
error codes while retaining only closed categories in job messages. Never retain
raw inference output, prompt, provider errors or private content as diagnostics.
Real provider-HTTP/worker regressions must fail first for these distinctions;
invented identities and unsupported proof must remain rejected atomically.

Actual inference on the first candidate found two retrieval failures before the
corresponding fixes: a compatibility path guard stopped discovery before the
real router/handler, documentation-heavy search consumed the card budget,
known response primitives became unresolved repository references, and semantic
planning repeated owner-file headers instead of selecting implementation bodies.
Adjacent labeled goal/acceptance sections also dropped acceptance conditions.
Focused worker/provider-HTTP and populated capture regressions cover these
boundaries. Dispatch retrieval distinguishes a handler call from a guard and
follows calls on the following branch lines. Search prioritizes application
implementation, and known response primitives are leaf operations. Semantic
refinement explicitly asks for behavior windows using the existing pinned symbol
index. Budgets, tools, authentication and baseline selection are unchanged.

The existing browser-validation composite action runs one representative
column-audit lifecycle journey through its test-only backend and reuses the
already built frontend. It uploads its sanitized receipts and browser artifacts.
Existing beta/main browser jobs use the `helm-runners` / `homelab-heavy` pool.
The existing hosted PR path remains necessary because that runner group's live
workflow admission excludes PR refs; this work changes no concrete job selector,
runner infrastructure, admission policy, or dependency lockfile.

Actual diagnostic model probe identified discovery_range: the schema bounded
absolute line numbers but neither schema nor instructions specified the server
window width of 101 lines. Regression checks must fail before instructions are
updated, and actual inference must retain the existing strict server range gate.

After bounded-range guidance, actual semantic inference selected owner headers
and unrelated helpers, then exhausted the unchanged per-card read budget. The
pinned server health body is declaration 42, beyond the first 40 signature index.
A late-function fixture must fail before replacing prefix-only index truncation
with a bounded whole-file sample. Planning should reserve the same file/discovery
ceilings for deliberate production ownership reads and relevant body refinement.

Actual health completion/correct inference was rejected specifically for a null
`target_column_id`, not missing proof. Test-first populated worker cases cover
server binding of absent target IDs and correct-card source state, while explicit
conflicts, ambiguous Backlog/Bugs mappings and invented citations remain rejected.
Only the internal inference target contract is simplified; public persisted v2
assessments still contain actual captured identities and full proof validation.

Uniform whole-file sampling can also omit middle declarations. The final bounded
index compacts declaration names with exact source line numbers into the same
40-by-160 signature envelope before sampling exceptionally large owners. A
second red regression covers a middle declaration hidden by uniform sampling.

# Helm v0.2.0

Helm v0.2.0 brings Tickets, HTTP and email alert intake, and guided
Cloudflare public access to production.

See the [release plan](../RELEASE_V0_2_0_PLAN.md) for the promotion sequence.

## Features

- **Tickets workspace:** A dedicated list and detail view for human triage,
  with open, assigned, Needs triage, Ready, In progress, Waiting and
  Completed queues. Create tickets, assign them to yourself, set priority,
  add notes, and accept, start, wait, complete or reopen work. Ticket
  membership survives label changes, and stale edits show a conflict.
- **One ticket queue:** New tickets from webhooks, email inboxes, Coolify
  and **New ticket** land in **Tickets → Needs triage**, without choosing
  a project. Queue tickets show **Not filed** and keys such as `TKT-12`.
  **Project** files a ticket into a project during triage, gives it the
  project's next key, and preserves old links, notes, evidence and repeat
  tracking. Filing is optional. Guide:
  [Where tickets land](../TICKET_WEBHOOKS.md#where-tickets-land).
- **HTTP webhooks:** Administrators create URLs for Generic JSON or
  Coolify notifications in **Tickets → Connect apps**. Generic JSON can
  include priority, source, a link and facts; a deduplication key counts
  repeats on the open ticket without overwriting human edits. Secrets are
  shown once, with rotation and disabling available later. **Send test**
  opens a real ticket through the public URL. Guide:
  [Ticket webhooks](../TICKET_WEBHOOKS.md).
- **Coolify alert intake:** Coolify's `traefik_version_outdated` notices
  open human-assigned tickets with an Alert source panel. Repeats count on
  the same condition without reopening completed work; a new offered
  version creates linked follow-up work. Both admin-created Coolify
  webhooks and the operator-configured intake route are supported. Guide:
  [Coolify webhook intake](../COOLIFY_EMAIL_INTAKE_PLAN.md#implemented-v1-webhook-intake).
- **Email inboxes:** Create named inboxes with addresses that stay visible,
  **Copy** and **Email it** actions, optional assignment, delivery counts,
  address replacement and disabling. Cloudflare Email Routing and an
  Email Worker turn mail into tickets without mailbox passwords or IMAP
  polling. Replies and repeated alerts count on the open ticket; duplicate
  delivery of the same message changes nothing. Recent emails explain
  refused mail, and a fallback address can receive mail Helm cannot
  accept. Webhooks remain HTTP-only. Guide:
  [Email inboxes](../PUBLIC_ACCESS.md#email-inboxes).
- **Connect Cloudflare:** **Reach Helm from outside** guides administrators
  through sign-in or a pre-filled API-token setup, domain selection, a
  public webhook URL and an optional first email inbox. A live checklist
  shows setup progress, then Helm forgets the Cloudflare credential. The
  sign-in option currently requires membership of the KanterLabs
  Cloudflare account; other installations use the token option. Guide:
  [Set up with Cloudflare](../PUBLIC_ACCESS.md#set-up-with-cloudflare).
- **Public access diagnostics and help:** Public URLs use Cloudflare
  Tunnel and a separate listener that exposes intake routes and probes
  while keeping the dashboard and other API routes private. Connector
  status, **Test public URL**, history and **Finish cleanup** help diagnose
  delivery and remove leftover Cloudflare resources. **Learn more** opens
  the guides inside Helm; details and manual setup are available below the
  connection summary. Guide:
  [Public URL](../PUBLIC_ACCESS.md#public-url-cloudflare-tunnel).

## Upgrade notes

- Updated the build dependency `source-map-js` from 1.2.1 to 1.2.2; the
  dependency audit reports no known vulnerabilities.
- The built-in Tickets queue is created on first use and hidden from
  ordinary project navigation. Agent tokens need an explicit grant to
  that project to access queue tickets.
- On the same installation, existing webhook URLs and inbox addresses
  keep working; new deliveries go to the ticket queue. Existing tickets
  stay where they were filed. The project-scoped ticket creation route
  remains available, and webhook and inbox creation still accept the
  legacy `project` input.
- `HELM_COOLIFY_PROJECT` is **deprecated and ignored**. Coolify intake
  uses the ticket queue; the webhook secret and assignee are still
  configured per installation. Settings:
  [CONFIGURATION.md](../CONFIGURATION.md).
- Beta and production have separate databases, integration credentials,
  webhooks, inboxes and Cloudflare resources. Promotion does not copy beta
  integrations into production. Create production integrations and
  re-point each app, verifying a real delivery before moving to the next.
- Production uses **`hooks.helm.shanekanterman.dev`** and the email address
  name **`helm`** (for example,
  `helm+homelab-alerts-x7k2qm@shanekanterman.dev`). Keep these distinct from
  beta's `hooks.shanekanterman.dev` and `helm-alerts` routing rule; do not
  share a tunnel or routing rule between environments. The hooks hostname
  must allow webhook delivery without a Cloudflare Access login redirect.

## Database compatibility

Upgrading from v0.1.1 applies seven additive migrations, **029–035**:

| Migration | Addition |
| --- | --- |
| 029 | Alert conditions and correlation for Coolify intake. |
| 030 | Durable ticket membership and backfill of alert tasks. |
| 031 | Administrator-managed ticket webhooks. |
| 032 | Public endpoint records. |
| 033 | Email intake, receipt history and the initial webhook email-tag columns. |
| 034 | Email inboxes, replacing per-webhook email addresses. |
| 035 | Built-in ticket queue marker and old task-key aliases for project filing. |

No existing tables or data are removed. The v0.1.1 binary is designed to
open the newer schema, so binary rollback does not require restoring the
database; new ticket and integration data remains for a later roll-forward.
After rollback, the built-in queue appears as an ordinary Tickets project.
Do not archive, rename, or change that project's columns with the old UI.
Pause webhook and email delivery during rollback: v0.1.1 does not implement
the intake routes. Preserve the upgraded database and connector files for
roll-forward. Backup and rollback procedure:
[OPERATIONS.md](../OPERATIONS.md#release-backup-and-rollback).

## Verification

- A verified production backup on 2026-10-11 contained 10 projects and
  1,087 tasks at schema 28. The candidate's preflight and upgrade to schema
  35 passed integrity and foreign-key checks. Every original row across
  all 34 existing tables survived migration, and the source backup's
  checksum remained unchanged. Migration on the rehearsal copy took
  0.432 seconds; this is not a production timing guarantee.
- The actual retained v0.1.1 production binary started against schema 35,
  read existing work, updated a task, and created another task. Returning
  to v0.2.0 preserved both writes and a new queue ticket. Original project
  and task identifiers, user data, and relationships remained intact.
- The deployed beta revision `9d23fa2` passed the
  [October 5 CI run](https://github.com/KanterLabs/helm/actions/runs/37245993377):
  79 normal browser workflows and local onboarding, with no unexpected
  or flaky outcomes. The evidence bundle's checksums were verified.
- Release CI repeats the browser workflows with the race detector,
  stalled-account scenarios, frontend and OpenAPI checks, Go vet,
  dependency scans, deployment-security checks, and container smoke tests.
  Production installation takes another verified backup and migration
  preflight before changing the active binary.

Production Cloudflare endpoints and inboxes require the separate setup
described above; beta integration resources are not moved by this release.

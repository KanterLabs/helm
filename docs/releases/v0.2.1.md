# Helm v0.2.1

Helm v0.2.1 promotes beta improvements to agent status, navigation, draft
protection and responsive board controls.

## Improvements

- **Clearer agent status:** Work state, check-in freshness and claim validity
  appear independently. Agent details show the next action and durable
  progress, with clearer timestamps and accessible status descriptions.
- **Navigation that remembers context:** Board criteria and task Activity
  survive reloads and browser history. Project Progress also restores its
  place. Saved searches can be refined without silently changing their stored
  definition; clearing editable criteria preserves the saved view's scope and
  sorting, while **New search** resets the search.
- **Safer creation:** Task, bug, project and quick-add creation protect pending
  submissions from dismissal and duplicate submission. Retries after a lost
  response preserve the original request and idempotency key. Validation
  failures retain editable drafts, and changing projects cannot submit stale
  destination columns.
- **Updates that protect drafts:** PWA updates respect unsaved forms, task
  edits, comments, checklist changes and ticket notes. Pending writes defer
  activation; canceled updates preserve the draft. **Later** dismisses the
  current version, and failed update attempts offer a retry.
- **Reachable board controls:** Compact card menus provide movement actions
  and restore focus after rejected moves. Responsive filter controls show
  active criteria and explain unavailable options. Columns fit the viewport,
  and the pinned sidebar keeps long project lists from scrolling the page.
- **Smoother ticket triage:** When an action removes a ticket from the current
  queue, selection advances to the next available ticket.

## Deployment and compatibility

Production follows validated pushes to `main` through the existing Helm CI
workflow. After checks, browser tests, race checks and the container build
pass, CI deploys the tested image by immutable registry digest to the
configured Coolify production service, provided production deployment is not
paused and the revision remains the branch tip. The deployment job checks
private readiness and records deployment evidence. See the
[Coolify deployment guide](../../deploy/coolify/README.md) for configuration
and rollback details.

There are **no database migrations** in v0.2.1. Current production and this
release use schema **35**. Production retains its separate database,
credentials and integration resources. See
[backup and rollback](../OPERATIONS.md#release-backup-and-rollback) and the
[previous release](v0.2.0.md) for the schema 35 upgrade history.

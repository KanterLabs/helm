# Helm v0.2.0 product knowledge

Verified against the published v0.2.0 release on 2026-10-15. Released
2026-10-11. This reference describes that release; check the live API's
`/openapi.json` before using an unfamiliar operation on another version.

The schema compatibility described below is historical. A current deployment
must also satisfy its current authorization admission floor and rollback policy;
this reference does not establish eligibility for a retained older binary.

## Tickets and project work

- Tickets have a dedicated human triage workspace with Needs triage, Ready,
  In progress, Waiting, and Completed queues, plus open and assigned views.
  People can assign tickets, set priority, add notes, accept, start, wait,
  complete, and reopen them. Ticket membership survives label changes.
- New tickets from webhooks, email inboxes, Coolify, and **New ticket** land
  in **Tickets → Needs triage**, without choosing a project. Unfiled tickets
  have keys such as `TKT-12` and show **Not filed**.
- Filing with the **Project** menu moves the ticket to a project and gives
  it the project's next key. Old links, notes, evidence, and repeat tracking
  survive. Filing is optional; tickets can be completed in the queue.
- The built-in queue is created on first use and hidden from ordinary
  project navigation. Agent tokens need an explicit grant to that project.
  Missing queue results do not mean there are no tickets; do not widen
  credentials to work around the project ceiling.
- `GET /api/v1/tickets` lists visible ticket queues. The older
  `POST /api/v1/projects/{project}/tickets` route remains available.
  Discover `createQueueTicket` and `fileTicket` in the live OpenAPI contract
  for queue creation and filing. The bundled workflow CLI does not provide
  dedicated ticket or integration commands; do not invent CLI subcommands.
- Tickets are not automatically bugs or claimed agent work. Continue to
  use the existing project task, claim, and progress workflow for substantive
  agent work; intake alone does not authorize acting on an alert.

## Webhook and email intake

Administrators manage Generic JSON and Coolify webhooks in **Tickets →
Connect apps**. A webhook secret is shown once, with rotation and disabling
available later. Treat the entire secret-bearing URL as a credential; do not
put it in chat, tracking cards, logs, or shared links. **Send test** opens a
real ticket through the public URL.

Generic JSON posts without a `dedupe_key` open a ticket every time. With a
key, repeats on an open ticket increase its occurrence count without
overwriting human edits or assignment. A delivery after completion opens
linked follow-up work. Coolify's `traefik_version_outdated` correlation is
condition-specific: repeats do not reopen completed work; a newly offered
version creates linked follow-up work.

Email inboxes are separate from HTTP webhooks. Cloudflare Email Routing and
an Email Worker deliver mail to Helm without mailbox passwords or IMAP
polling. Inbox addresses remain visible and support copying, replacement,
disabling, optional assignment, and delivery counts. Replies and repeated
alerts count on the open ticket; delivery of the same Message-ID again
changes nothing. Recent emails explain refused mail, and a fallback address
can receive mail Helm cannot accept. Disabling intake preserves tickets.

## Public access

**Reach Helm from outside** guides administrators through Cloudflare
authentication, domain selection, a public webhook URL, and an optional
first email inbox. The sign-in option in this release requires KanterLabs
Cloudflare account membership; other installations use the API-token path.
Helm forgets the Cloudflare setup credential after setup.

Cloudflare Tunnel connects to a separate intake listener. Only intake routes
and probes become public; the dashboard, sign-in, and other API routes stay
private. Connector status, **Test public URL**, history, and **Finish
cleanup** support diagnosis and cleanup. Public URL probes do not create a
ticket; webhook **Send test** does.

Beta and production have separate databases, integration credentials,
webhooks, inboxes, and Cloudflare resources. Promotion does not copy beta
integrations. For Shane's installation, production uses
`hooks.helm.shanekanterman.dev` and the email address name `helm`; beta uses
`hooks.shanekanterman.dev` and `helm-alerts`. Do not share a tunnel or email
routing rule between those environments. Webhook delivery must not be
redirected to Cloudflare Access login.

## Upgrade and rollback

- `HELM_COOLIFY_PROJECT` is deprecated and ignored; Coolify intake uses the
  built-in queue. Existing webhook URLs and inbox addresses on the same
  installation keep working, with new deliveries entering the queue.
  Existing filed tickets stay in their projects.
- Upgrading from v0.1.1 adds migrations 029–035 (schema 28 to 35), preserving
  existing tables and data. They add alert correlation, ticket membership,
  webhooks, public endpoints, email intake/inboxes, and queue/key aliases.
- The retained v0.1.1 binary supports opening the newer schema. Binary
  rollback does not require restoring the database. Keep the upgraded
  database and connector files for roll-forward; pause webhook and email
  delivery because v0.1.1 lacks those intake routes. In its old UI the queue
  appears as an ordinary Tickets project: do not archive it, rename it, or
  change its columns. Follow the skill's verified-backup and populated-data
  validation requirements before any actual upgrade.
